This document outlines the two-gate privacy pipeline, GDPR Article 9 cryptographic pseudonymization, dedicated Model Armor security templates, and our interactive verification harness.

⚠️ Checkpoint ③ is the #1 blind spot in modern agent architectures: Most developer quickstarts only protect ① & ④, leaving the agent completely vulnerable to indirect prompt injection from fetched training logs, external RSS feeds, or calendar payloads.

In modern agentic architectures, vulnerabilities shift from the user prompt boundary to external tool outputs and autonomous mutations:

  • Checkpoint ① (Ingress Boundary): Evaluates direct user input at the edge before container execution using regional Model Armor templates (rowing-coach-guardrails). Detects adversarial jailbreaks (PI/JB v1.2) and malicious URLs, immediately returning a friendly squad refusal without consuming LLM inference tokens.
  • Checkpoint ② (Tool Call Gate): Intercepts mutating actions on external systems (e.g., intervals_schedule_workout). Enforces strict parameter schema verification and interactive human confirmation (require_confirmation=True), preventing unauthorized calendar mutations.
  • Checkpoint ③ (Tool Output Shield): Screens data fetched by external tools (e.g. Intervals.icu wellness logs, Concept2 workout history, FFAviron regatta calendars, or Google Search snippets) before it is appended to conversation history. Without this shield, untrusted external content containing embedded injection instructions can hijack model context (OWASP LLM01). In ADK 2.12+, this is handled natively via tool_output_template_name; in ADK 2.4.0, sub-agent architectural isolation (research_agent via AgentTool) and friendly_block provide inline protection.
  • Checkpoint ④ (Egress Boundary): Evaluates outbound model completions using a dedicated template (rowing-coach-guardrails-output). Enforces Sensitive Data Protection (SDP) to mask inadvertent PII or credential leakage, while deliberately disabling PI/JB filters on egress so that discussing safety rules never causes self-censorship false blocks. Finally, Gate 2 client rehydration verifies zero orphan token leakage (VaultSafetyError).

Section 3

GDPR Article 9 & Cryptographic Pseudonym Architecture

Under European Union law (GDPR Article 9), physiological metrics, heart-rate zones, resting HRV, and injury notes are classified as Special Category Health Data. Processing this data requires explicit safeguards:

  1. Zero PII in Model Weights or Cloud Logs: Real names, telephone numbers, and email addresses are replaced at the ASGI boundary before prompts touch Vertex AI or Google Cloud Logging.
  2. Cryptographic Pseudonymization: Rather than assigning random tokens like [ATHLETE_NAME_1] (which destroys context and prevents the agent from opening the rower's file), the vault computes deterministic SHA-256 tokens matching the squad database in data/athletes.json (e.g. [ATHLETE_ath_5a77195e] for David Montgomery).
  3. Algorithmic Tool Unwrapping: When the orchestrator delegates to deterministic physics or Wolverine L4 calculation tools (calculate_athlete_pacing, align_session_pace_to_l4), the tool code unwraps the pseudonym to access benchmark splits, returning calibrated target wattages and splits to the model.
  4. Gate 2 Reversible Client Rehydration: On the egress boundary, Gate 2 restores the athlete's friendly name for the coach's browser display, while asserting zero unmapped orphan tokens (VaultSafetyError).

The 3-Tier Athlete Identity Resolution Hierarchy

When sovereign boundaries separate the client browser, the local proxy, and the remote reasoning engine, identity representations diverge across execution tiers. The agent solves this with an explicit 3-tier translation hierarchy:

Tier Identity Representation Scope & Storage Boundary Example Value
Tier 1: Client Raw Persona Natural user-provided athlete or coach name Client browser DOM & local session state only; never sent over cloud network unredacted. "Coach David Montgomery" / "Coach David"
Tier 2: Gate 1 Cryptographic Vault Token Deterministic SHA-256 pseudonym token Pure-ASGI proxy network boundary; ensures GDPR Art. 9 compliance without leaking PII. "[ATHLETE_ath_5a77195e]"
Tier 3: Reasoning Engine Internal Roster Key Internal stable squad roster identifier Remote Vertex AI Reasoning Engine & tool database (data/athletes.json, agent instructions). "david_montgamery" (benchmark 2k split 1:58.2, 211.9W)

Pre-Dispatch Translation & Egress Rehydration Bridge: Direct token passing fails because remote engine instructions specifically instruct the LLM to index david_montgamery. Prior to cloud dispatch, local_proxy.py applies a pre-dispatch dictionary mapping (pseudo_to_engine) that translates [ATHLETE_ath_5a77195e] to david_montgamery. On egress, Gate 2 pre-rehydrates david_montgamery back to raw_coach before invoking vault.rehydrate(), guaranteeing that the coach sees natural names while fail-closed VaultSafetyError guards against orphan tokens.

Live Reviewer Access & Identity Architecture: The IAP Trade-Off

For the GDG London Hackathon showcase, a live evaluation entry point was deployed to Google Cloud Run to enable organizers and judges to interact with the agent end-to-end:

💡 Identity-Aware Proxy (IAP) Evaluation: Why Considered, Why Not Retained

We evaluated Google Cloud Identity-Aware Proxy (IAP) to secure access to the Cloud Run deployment. While IAP provides enterprise zero-trust identity verification via Google Workspace / Cloud Identity at the Cloud Load Balancer boundary, it was deliberately not retained for the hackathon. Hackathon judges, mentors, and peer evaluators utilize a diverse mixture of personal Google accounts, corporate workspace tenants, and external organizational emails. Requiring every evaluator to be individually pre-provisioned in Google Cloud IAM or navigate OAuth consent authorization screens introduces unacceptable onboarding friction during a rapid 3-minute pitch.

Retained Access Architecture: Fail-Closed Ephemeral Gating

Instead of introducing IAM onboarding friction, the live Cloud Run entry point implements a fail-closed application gate:

  • Pseudorandom Token Generation: The evaluator access code was generated using a cryptographically secure pseudorandom generator. The specific generator and its seed mechanics are intentionally kept confidential as a defense-in-depth measure against theoretical PRNG vulnerabilities or seed prediction. Neither the internal format nor the raw token is ever disclosed publicly or committed to source control.
  • Strict Secret Hygiene: The repository code and public commits contain strictly masked representations (rowing-********-devcamp-2026). The active secret is injected exclusively at runtime via Cloud Run environment variables (DEMO_PASSCODE) and communicated privately to judges in the hackathon portal submission.
  • Hardware Ceiling & Anti-Denial-of-Wallet: The Cloud Run service enforces strict hardware limits (--max-instances 1, --min-instances 0, 512MiB RAM, 1 vCPU), paired with Cloud Billing budget caps. Even under adversarial crawler probing, compute and inference costs cannot exceed the fixed hardware ceiling, scaling to zero immediately when idle.
  • Fail-Closed Session Gating: Requests without valid credentials receive a sleek dark-mode lock screen (HTTP 200). Direct unauthenticated API calls (/api/chat) return HTTP 401 Unauthorized. Evaluators accessing the direct reviewer URL (?code=...) are automatically issued an HTTP-only session cookie that unlocks the coaching dashboard for their review session.
